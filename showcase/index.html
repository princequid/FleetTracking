Project Overview

From manual chaos to a single source of truth

A delivery company running vans has no reliable idea where they are. FleetSync Pro replaces phone calls, paper logs and on-phone photos with one enforced system.

The problem

Fleet operations today rely on three fragile manual channels:

  • “Where are you?” phone calls between dispatcher and driver
  • A paper or spreadsheet log of who took which vehicle — stale by the time it’s read
  • Proof-of-delivery photos that live on the driver’s phone
  • “Was that delivery late?” — nobody knows

The solution

One system that unifies all three into an enforceable, observable platform:

  • Live vehicle positions on a map
  • A trip lifecycle the system enforces end-to-end
  • Proof-of-delivery stored centrally, attached to the trip
  • Recorded ETA and actual completion time for every trip

Key benefits

Why it beats the manual process — three concrete things, not just “it’s digital”:

  • Position updated roughly every 2 seconds, no calls needed
  • Vehicle status is a state machine — an IN_USE vehicle cannot be assigned
  • POD retrievable months later from object storage
  • On-time rate and audit trail measured across hundreds of trips
System Workflow

The lifecycle of a delivery, end to end

From trip creation to completion, every transition is enforced by the system — the answer most likely to be asked first, so it is told as a story.

Step 01 · Dispatch

Trip creation

The dispatcher creates the trip in the admin portal — driver, vehicle, origin, destination, and any intermediate stops.

Step 02 · Reservation

Validation & reservation

trip-service calls driver-service and vehicle-service to confirm availability, then sets the vehicle to IN_USE so nobody else can take it. The trip is written with status ASSIGNED.

Step 03 · Reliability

Event recorded, not sent

In the same database transaction as the trip, a trip.created row is written to an outbox table — nothing is lost if the broker is down.

Step 04 · Departure

Driver starts

Status moves ASSIGNED → STARTED → EN_ROUTE. From this point the phone streams GPS positions roughly every 2 seconds.

Step 05 · Tracking

GPS tracking & live map

gps-service rejects implausible pings, caches the latest position in Redis, writes it to Postgres, and pushes it over a WebSocket — the dispatcher’s map moves in real time.

Step 06 · Arrival

Geofence check

The driver arrives — a geofence check confirms they are within 50 m of the destination and status becomes ARRIVED.

Step 07 · Verification

Proof of delivery

The driver photographs the delivery. The photo uploads directly to MinIO using a presigned URL — the image never passes through the API.

Step 08 · Completion

Completion & release

trip-service verifies a POD exists, sets the trip DELIVERED, and releases the vehicle back to AVAILABLE. Downstream, notification-service emails and audit-service records the trail.

Security

Defence in depth, from the edge to the data

A structured audit found and fixed roughly 40 issues. These are the layers that keep the platform hardened — and the two findings that remain honestly open.

Core

JWT validated at the gateway

Every external request is authenticated once, at the edge — before it consumes a thread or connection downstream. Services implement only authorization.

Core

Header overwrite, not append

X-User-Id and X-User-Role are set from the validated token, so a spoofed X-User-Role: ADMIN header is discarded on every request.

Core

Internal calls verified

Service-to-service calls need the internal secret and the absence of a user role — a user request always carries a role, so it can never be mistaken for internal.

Hardening

Refresh-token rotation

7-day revocable refresh tokens rotate on use; presenting a spent token revokes the entire token family — the only realistic explanation is theft.

Hardening

BCrypt cost 12

Password hashing uses BCrypt with cost factor 12, plus account lockout after 5 failed attempts for 15 minutes — counted atomically in the database.

Hardening

Rate limiting

Requests are rate-limited at the gateway to blunt credential stuffing and abuse of high-volume endpoints.

Hardening

TLS everywhere, minimal surface

Caddy terminates TLS with automatic Let’s Encrypt certificates. Public ports are 22, 80 and 443 only; business services use Docker expose, never published to the host.

Hardening

Redis hardened

An unauthenticated Redis is a remote-code-execution primitive — it now runs with --requirepass and loopback-only binding.

Hardening

Presigned uploads only

POD photos upload directly to MinIO with a signed URL — large uploads never pass through the API, and storage access stays verifiable.

Still open — stated honestly

The JWT secret and a Google Maps Android key sit in git history and need rotating; purging the Maps key is what keeps the CI secret scan red. There are also no automated backups yet (see Known Limitations).

Scaling Strategy

From 50 drivers to 10,000

Which component breaks first, and how do you fix it? Do the arithmetic out loud — 10,000 drivers × 1 ping / 2 seconds = 5,000 writes/second.

50

Today · single VM, comfortably running

The full stack runs on one e2-standard-2 (2 vCPU, 8 GB RAM). Every service is healthy and the entire load profile is far below capacity.

50 drivers ≈ 25 pings/s 17 containers
500

Steady growth · uneven load pays off

~250 pings/s — still well within PostgreSQL’s simple-insert capability. The service split earns its keep: gps-service’s write volume scales and throttles independently of the low-traffic vehicle-service.

500 drivers ≈ 250 pings/s gps-service scales alone
5k

Approaching the edge · table pressure builds

~2,500 pings/s. Raw inserts are fine — the unpartitioned gps_pings table is not: index maintenance degrades and autovacuum starts falling behind as rows accumulate.

5,000 drivers ≈ 2,500 pings/s index maintenance autovacuum
10k

First bottleneck · gps_pings by a wide margin

5,000 writes/s → ~144 million rows per day. Everything else is comfortable at this scale; this table is not. The fix is partitioning plus retention, not raw insert speed.

10,000 × ½s = 5,000 writes/s 5,000 × 3,600 × 8h ≈ 144M rows/day
Second bottleneck — WebSocket fan-out One dispatcher watching all 10,000 vehicles is 5,000 messages per second to one browser, which no browser will render. That is a product problem before an engineering one: the map should stream only the vehicles in the current viewport.

Fixes, cheapest first

  1. Partition gps_pings and add retention Partition by day or week and drop old partitions instead of deleting rows — dropping a partition is instant; DELETE on 144M rows is not. Nobody needs second-by-second history from six months ago.
  2. Batch on the client Send one request with 15 pings every 30 seconds instead of 15 separate requests. Same data, one-fifteenth of the HTTP and transaction overhead — already on the roadmap.
  3. Separate reads from writes The live map does not need Postgres at all — the latest position is already in Redis. Serve the map entirely from Redis and let Postgres be the historical archive only.
  4. Move the time-series data to a store built for it TimescaleDB is a PostgreSQL extension — the least disruptive version of that change for an append-only, time-ordered stream like gps_pings.
  5. Scale gps-service horizontally It is stateless, so this is easy — but only after the steps above, since more instances writing to one unpartitioned table makes the real problem worse, not better.
Known Limitations

Gaps, named honestly

Where something is not built, we say so — and we rank what would hurt most in production. An examiner who watches you name your own gap trusts the rest.

No backups Critical

Zero. If the VM’s disk fails, every trip, photo and audit record is gone. Not built because it needs somewhere to put them and a tested restore — the most serious gap in the project.

Fix: Week 1 — pg_dump plus a MinIO mirror to Cloud Storage on a cron, and a tested restore. An untested backup is not a backup.

Offline GPS queue is a stub High

A driver through a tunnel leaves a gap in the recorded track that is never filled. gpsQueueStore_2.js was intended to be the queue but contains a single comment line.

Fix: A ring buffer with a hard cap that batches on flush — each ping carries its own recordedAt, so the server back-fills the missing segment instead of showing a teleport.

Background tracking missing High

Tracking uses Location.watchPositionAsync, which is foreground-only — if the driver switches apps or locks the phone, tracking stops.

Fix: startLocationUpdatesAsync with a TaskManager background task, a persistent notification, and separate background-permission prompts.

No observability High

No metrics, no structured logs, no alerting — diagnosis is docker compose logs. We would find out about an outage from a user.

Fix: Actuator + Micrometer + Prometheus, alerting on symptoms users feel — not on CPU. You cannot operate what you cannot see.

Single point of failure High

One VM, one PostgreSQL, no replica. auth-service, the gateway and Postgres are hard dependencies — if any is down, so is the product.

Fix: A second node with replicas is the honest boundary — the point at which we would move from Compose to Kubernetes.

gps_pings unpartitioned Medium

No partitioning and no retention policy — the first bottleneck at scale (see Scaling).

Fix: Week 4 — partition by day/week, add retention, and batch pings from the client.

analytics-service is a stub Medium

No pom.xml, no main class. Its schema exists, nothing writes to it, and it is deliberately not deployed.

Note: Auditing and reporting today come from SQL aggregates over the existing schemas.

No push notifications Medium

Notifications default to email; in-app polling covers the current need.

Fix: Push would be the next channel, layered onto the same event bus.

With one more month, in order

Week 1

Backups

pg_dump + a MinIO mirror to Cloud Storage on a cron, and a tested restore. Converts an unrecoverable failure into an inconvenient one.

Week 2

Background GPS & offline queue

The product is called live tracking and currently stops when the driver locks their phone. Background task + ring-buffer queue.

Week 3

Observability

Actuator + Micrometer + Prometheus, and alerting on service health. You cannot operate what you cannot see.

Week 4

Partition & batch

Partition gps_pings, add retention, and batch pings from the client. None of these are features — they are the difference between a system that demos and a system that runs.

Weakly tested — stated plainly No integration tests — everything is unit-level with mocked collaborators. Testcontainers is the right tool and the biggest single gap. No mobile tests at all.
“A test that cannot fail is worse than no test.” It reports confidence it does not have. When the vehicle release moved to a dedicated endpoint, a stale test still passed — it was stubbing an exception on a method no longer called, so it was asserting nothing. It was rewritten to genuinely exercise the outage path.
Deliberately well tested: the vehicle-release rule

It has two opposite failure modes — not releasing strands vehicles, releasing too eagerly puts an unroadworthy van back into dispatch. The parameterised test over the other statuses exists to stop a future “simplification” back to a blanket status write.

Personal Contribution

What I built, decided, and learned

The structure that scores well: name the area → name a decision and the alternative you rejected → name a bug that was genuinely hard → say what you learned.

My contributions

  • Gateway security: JWT validation, header overwrite (set, not add), internal-call verification
  • Dedicated vehicle-release endpoint and reconciliation sweep for stranded vehicles
  • gps-service filtering: accuracy before plausibility on every ping
  • Outbox pattern for reliable trip.created events
  • Three-layer design tokens in the admin portal (dark mode remaps only the middle layer)
  • Structured security audit across portal, backend, infrastructure, CI and docs

Design decisions

  • Vehicle release via a narrow endpoint (IN_USE → AVAILABLE only) rather than the generic status endpoint — so a late-firing sweep can never drag a van out of MAINTENANCE
  • Rejected a monolith's shared tables for per-service schemas — a versioned API contract instead of silent runtime breakage
  • Self-hosted OSRM over a metered Directions API — cost and request volume
  • Would I do microservices again? No — a modular monolith, splitting out only gps-service

Challenges — bugs that were genuinely hard

  • Vehicles never returned to the fleet — completing a trip never released the vehicle. It looked like a display bug: the vehicle was on screen, just wrong.
  • Dark-mode contrast at 1.46:1 — a token used for the wrong job; the fix was conceptual, not cosmetic
  • Stale-jar false positive — grepped the deployed jar, found the string, concluded the fix was live. The old code contained the same string.
  • ETA column overflow — 146 px column, 203 px of content; measured against the built stylesheet rather than eyeballed

Lessons learned

  • A check that cannot fail proves nothing. The real proof was the compiled constant pool — two constants meant old, one meant new.
  • Architecture can create bugs. One boolean — is this van in use — had to stay consistent across two services with no shared transaction. That is the cost a service boundary creates.
  • The real test of a boundary is not “is this a different noun?” but “does this need to scale, fail, or deploy differently?”
  • Name your own gaps. An examiner who finds a gap you claimed was covered will discount everything else you said.
